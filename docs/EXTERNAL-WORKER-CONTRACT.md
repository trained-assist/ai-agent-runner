# Контракт внешнего serverless worker (issue #73, эпик #74)

Канонический контракт запуска агента во внешнем воркере. Заменяет синхронный
`LaunchRequest → LaunchResult` (один долгий HTTP-вызов, соединение живёт весь ран)
на асинхронный цикл **receipt → status → result** с дедупликацией по `operationId`.

## Приоритетная цепочка движков (issue #100)

У API может быть несколько воркеров — по одному на движок. Порядок проб задаёт конфиг
`AGENT_API_ENGINE_CHAIN` (для текущей очереди `eu-vm-agent-run,rf-vm-agent-run,azure-dynamic-ip-agent-run`),
а не сортировка имён: приоритет — решение владельца, и алфавит его не выражает.

| Шаг | Движок | Где | Роль |
|---|---|---|---|
| 1 | `eu-vm-agent-run` | наша France VM | основной VM worker |
| 2 | `rf-vm-agent-run` | наша Russia VM | следующий VM worker |
| 3 | `azure-dynamic-ip-agent-run` | GitHub Actions, внешний Azure worker | serverless резерв |

Capacity response `WORKER_CAPACITY` from either regional VM preserves 40% host headroom
and cuts the new run directly over to GHA, skipping any remaining regional VM.
`WORKER_CAPACITY_UNKNOWN` and `WORKER_ADMISSION_UNAVAILABLE` do not prove saturation, so
they follow the configured regional order. Once any worker accepts, the run is not moved.

### Бюджет приёма рана

У каждого движка свой бюджет ожидания квитанции: `acceptDeadlineMs` в `AGENT_API_WORKERS`
либо общий `EXTERNAL_WORKER_ACCEPT_DEADLINE_MS` (по умолчанию 30 с — стартовое значение
для GitHub Actions, подбирается по замерам). Это отдельная величина от таймаута запроса:
«воркер не ответил» и «ран идёт долго» — разные события с разными бюджетами.

### Когда цепочка двигается

Переход к следующему движку допустим **только если ран не принят** — квитанции нет:

| Отказ | Переход |
|---|---|
| `WORKER_LAUNCH_UNREACHABLE` (нет ответа за бюджет) | да, но сначала reconcile (см. ниже) |
| `WORKER_HTTP_ERROR` (воркер ответил ошибкой) | да, но сначала reconcile |
| `WORKER_PROTOCOL_INVALID` (ответ вне контракта) | да, но сначала reconcile |
| `WORKER_CAPACITY` (подтверждённый предел 60%) | для France/Russia — сразу GHA, без промежуточной VM |
| `WORKER_CAPACITY_UNKNOWN` / `WORKER_ADMISSION_UNAVAILABLE` | следующий worker по очереди; отказ доказывает, что запуск не принят |
| квитанция получена | **нет**: ран уже идёт, дальше только reconcile |
| `unknown` (исход не установился) | **нет**: повод спрашивать принявший движок, а не запускать заново |
| отказ на стороне API (нет промпта, `refs` без workspace, не задан `resultUrl`) | **нет**: другой движок его не обойдёт |

### Reconcile перед переходом

Отсутствие квитанции само по себе не доказывает, что запуск не состоялся: запрос мог дойти,
воркер мог зарегистрировать и запустить агента, а ответ потеряться (контракт, п. 4). Поэтому
перед переходом к следующему движку цепочка спрашивает текущий: `GET /v1/runs/{runId}/status`.

| Ответ воркера | Решение цепочки |
|---|---|
| ран известен (`accepted`/`running`/терминальный) | перехода нет: ран принимается без квитанции и опрашивается здесь же |
| `unknown` (ран не зарегистрирован) | переход к следующему движку — запуск доказанно не состоялся |
| спросить не удалось | перехода нет: ран остаётся `unknown`, второй запуск без доказательства запрещён |

Это же правило работает и для единственного движка: контракт не различает «цепочка» и
«один исполнитель» — везде сначала reconcile, и только отрицательный ответ даёт право на
второй запуск.

### Идемпотентность сквозь цепочку

`operationId` и `runId` при переходе не меняются. Если первый движок принял ран после
того, как бюджет истёк, его дедупликация по `operationId` возвращает тот же `runId`, а не
второй запуск. Отметка о приёме (`dispatched`) пишется в журнал до старта поллера, поэтому
после рестарта API опрос продолжается у движка, который ран принял, — а не у первого в цепочке.

### Кто видит результат цепочки

`RunStatusView.engine` — фактический движок: тот, на котором идёт попытка приёма, а после
квитанции — тот, который ран принял. Отмена и поллер рана ходят именно к нему. Заявка с
явным `engine.name` цепочкой не пользуется: названный движок — единственный кандидат.

### Исчерпанная цепочка

Если ни один движок не принял ран, он закрывается `failed` с кодом `ENGINE_FLEET_EXHAUSTED`
и перечнем попыток (`<движок>: <код>`). Это не `unknown`: выполнять ран некому, и обещать
reconcile несуществующего запуска было бы враньём. Новый `Idempotency-Key` даёт новую
попытку.

### Региональные ограничения

Цепочка не фильтруется по `regionConstraints`: ограничения едут в спецификации рана каждому
кандидату, и движок, который не может их выполнить, обязан отказать. Отказ размещения
отличается от транспортного отказа только кодом в перечне попыток — различить их на стороне
API нельзя, поэтому отказ тоже двигает цепочку.

## Зачем меняется

Текущий контракт (`src/adapters/external-worker-adapter.ts`) заставляет API держать
HTTP-соединение на весь ран и возвращать финальный результат в том же ответе. Отсюда:

- **потеря связи = потеря результата**: обрыв посреди прогона даёт
  `WORKER_LAUNCH_TIMEOUT` с `retryable: false`, хотя ран на воркере живёт и
  завершится — результат некому забрать;
- **нет восстановления после рестарта API**: у API нет способа спросить «что с этим
  раном», не запуская заново;
- **повтор с новым ключом не является recovery**: новый `operationId` плодит второй
  ран там, где первый ещё идёт.

## Границы

| Слой | Ответственность |
|---|---|
| Control plane / D1 / Workflow | authoritative task/run ownership, `operationId`/`generation`, status/result/artifact/log refs, recovery. HTTP API может быть stateless adapter; in-memory receipts не источник истины |
| Worker | запуск engine, clean room, разрешённый input, scoped tools, upload/publish, teardown. Временный диск допустим: «нет долговечного локального состояния» ≠ «нет cwd и staging» |
| Worker/finalizer рядом с данными | сохраняет run branch, байты артефактов и журнал **до** уничтожения среды |

## 1. Асинхронный launch

`POST {worker}/v1/launch` принимает `LaunchRequest` и возвращает **квитанцию**, а не
результат:

```json
{
  "runId": "run_01J…",
  "operationId": "op_01J…",
  "status": "accepted",
  "statusUrl": "{worker}/v1/runs/run_01J…/status",
  "resultUrl": "{worker}/v1/runs/run_01J…/result"
}
```

`status: "accepted"` означает только «запуск принят и зарегистрирован». Финальный
результат читается отдельно. Соединение на весь ран не держится.

## 2. Дедупликация по operationId

Воркер обязан помнить принятые `operationId` (или выводимый из него ключ) и при
повторном `launch` с тем же ключом:

- возвращать **ту же квитанцию** и тот же `runId`, не запуская агента заново;
- если ран ещё идёт — текущий `status`;
- если ран завершён — квитанцию с финальным `status` и ссылкой на результат.

Без этого свойства повторная доставка запроса плодит второй ран — ровно тот класс
дефектов, который контракт обязан исключать.

## 3. Status и result — разные контракты

```
GET {worker}/v1/runs/{runId}/status   → { runId, status, updatedAt }
GET {worker}/v1/runs/{runId}/result   → LaunchResult | 409 (ещё не готово)
```

`status`: `accepted | running | succeeded | failed | cancelled | unknown`.

**Что уже учтено по боевой приёмке (04.10.2026, шлюз 136.65.7.197:8080):**

- `LaunchResult.pid` — **необязателен**: агент в GitHub Actions запущен на другой машине,
  локального PID у нашего API нет. Событие `started` без pid не выдумывается.
- `LaunchResult.repo.commit` — может быть `null` или null-SHA: это «в ветку ничего не
  запушено», а не отказ. Ссылка на файл тогда адресует ветку (`/tree/<branch>/<path>`),
  а не битый `/blob/null/...`; merge ведёт на страницу ветки.
- `logUrl` со схемой `local://` (воркер без бакета) — честный ответ, но не URL:
  `GET /v1/runs/{id}/log` отдаёт ссылку в теле с `retrievable: false`, а не редиректит.
- `status` в `LaunchResult` — `started | failed` про **запуск движка**, а не про исход рана;
  исход несут `exitReason`/`failure`.

`unknown` — исход, который нельзя установить (обрыв связи, смерть воркера без
финализации). Это **не** `failed`: задача не теряется, авто-rerun не происходит,
следующий шаг — reconcile существующего запуска.

## 4. Timeout после dispatch = unknown, затем reconcile

Таймаут ожидания ответа воркера **не** означает, что ран не запущен. Порядок:

1. пометить попытку `unknown` с причиной `worker_unreachable`;
2. **сначала** запросить `status` существующего запуска — ран мог стартовать и даже
   завершиться, пока не было связи;
3. только если запуск не найден — считать его не состоявшимся.

Отмена осиротевшего рана (`cancelOrphan`) остаётся лучшим усилием, но не
заменяет reconcile.

## 4.1 Что повторять, а что нет (`retryable`)

Наш API решает по `retryable`, можно ли уйти на другого исполнителя. Повтор имеет смысл
только там, где следующая попытка может дать другой исход:

| Код | retryable | Почему |
|---|---|---|
| `WORKER_LAUNCH_UNREACHABLE` | `true` | сетевой обрыв или таймаут: воркер мог не получить задачу вовсе |
| `WORKER_HTTP_ERROR` 5xx | `true` | состояние воркера, повтор оправдан |
| `WORKER_HTTP_ERROR` 4xx | `false` | отказ про запрос (битый общий секрет, неверный payload): тот же запрос получит тот же отказ |
| `WORKER_PROTOCOL_INVALID` | `false` | расхождение контракта детерминировано: тот же запрос вернёт тот же неверный ответ, и повтор станет штормом |
| `RESULT_URL_UNSET`, `WORKER_NOT_CONFIGURED` | `false` | не настроено у нас, повтор не поможет |

Квитанция получена — повтор запрещён в любом случае: ран уже где-то идёт, второй запуск
недопустим.

## 5. Два назначения repository — не смешивать

| Назначение | Ветка | Что делается |
|---|---|---|
| Кодовая задача рана | `agent-run/<runId>` | коммит от `baseRevision`, пуш **до** обновления основной ветки; durable-кандидат, переживающий смерть VM |
| Постоянный profile workspace | публикация run branch + versioned canonical merge | следующий Run читает накопленное состояние; конфликт — явный, не «последний победил» |

Основная ветка профиля не меняется автоматически. Смешивать два назначения в одном
repository нельзя: у них разные политики обновления и разный смысл конфликта.

## 6. Тяжёлые выходы — object storage, не git

Git хранит текст/дерево/манифест. Крупные и бинарные выходы — object storage с
хэшами. Ссылка на артефакт обязана быть **доступна конкретному пользователю**:
публичный blob URL из private repo не гарантирует скачивание нашим API-клиентом.
Нужен authenticated retrieval/proxy или scoped URL с принятой доступностью.

## 7. Изоляция воркера объявляется отдельно

Isolation API host может быть `none`, но isolation worker обязана быть отдельно
declared и verified. Snapshot/materialize, артефакты, MCP и interaction-гарантии
**переносятся или заменяются эквивалентом**, а не считаются ненужными из-за удаления
маршрутов.

## 8. Живые события и архив лога — разные контракты

Финальный `logUrl` в GCS не доказывает streaming/cursor replay. GCS-логи приватны,
доступ — scoped. Cleanup VM выполняется после подтверждённой recovery-копии, а не
после одного выхода engine.

## Что это даёт ближайшему deliverable

Один synthetic профиль через наш Task API выполняет настоящий external worker Run:
после рестарта API нет второго запуска, пользователь читает ответ и артефакт,
ephemeral ресурс исчезает только после persist, следующая среда видит сохранённые
данные. До этого #75/#76 не считаются завершённой serverless-миграцией.

## Task-scoped ingress manifests

`ingressManifest` is forwarded only to the France/Russia VM engines, whose packaged
Runner wires `ControlPlaneIngressResolver` from the trusted `RUNNER_CONTROL_PLANE_*`
bindings. The generic Azure/GitHub Actions worker has no configured resolver and is
refused locally with `INGRESS_MANIFEST_UNSUPPORTED` before submit. Do not drop the pin
or retry that run as a prompt-only task; configure a trusted resolver on that worker
before enabling the capability there.
