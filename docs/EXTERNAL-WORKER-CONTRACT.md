# Контракт внешнего serverless worker (issue #73, эпик #74)

Канонический контракт запуска агента во внешнем воркере. Заменяет синхронный
`LaunchRequest → LaunchResult` (один долгий HTTP-вызов, соединение живёт весь ран)
на асинхронный цикл **receipt → status → result** с дедупликацией по `operationId`.

## Зачем меняется

Текущий контракт (`src/adapters/external-worker-adapter.ts`) заставляет API держать
HTTP-соединение на весь ран и возвращать финальный результат в том же ответе. Отсюда:

- **потеря связи = потеря результата**: обрыв посреди прогона даёт
  `WORKER_LAUNCH_TIMEOUT` с `retryable: false`, хотя ран на воркере живёт и
  завершится — результат некому забрать;
- **нет восстановления после рестарта API**: у API нет способа спросить «что с этим
  раном», не запуская заново;
- **повтор с новым ключом не является recovery**: новый `operationId` плодит второй
  ран там, где первый ещё идёт.

## Границы

| Слой | Ответственность |
|---|---|
| Control plane / D1 / Workflow | authoritative task/run ownership, `operationId`/`generation`, status/result/artifact/log refs, recovery. HTTP API может быть stateless adapter; in-memory receipts не источник истины |
| Worker | запуск engine, clean room, разрешённый input, scoped tools, upload/publish, teardown. Временный диск допустим: «нет долговечного локального состояния» ≠ «нет cwd и staging» |
| Worker/finalizer рядом с данными | сохраняет run branch, байты артефактов и журнал **до** уничтожения среды |

## 1. Асинхронный launch

`POST {worker}/v1/launch` принимает `LaunchRequest` и возвращает **квитанцию**, а не
результат:

```json
{
  "runId": "run_01J…",
  "operationId": "op_01J…",
  "status": "accepted",
  "statusUrl": "{worker}/v1/runs/run_01J…/status",
  "resultUrl": "{worker}/v1/runs/run_01J…/result"
}
```

`status: "accepted"` означает только «запуск принят и зарегистрирован». Финальный
результат читается отдельно. Соединение на весь ран не держится.

## 2. Дедупликация по operationId

Воркер обязан помнить принятые `operationId` (или выводимый из него ключ) и при
повторном `launch` с тем же ключом:

- возвращать **ту же квитанцию** и тот же `runId`, не запуская агента заново;
- если ран ещё идёт — текущий `status`;
- если ран завершён — квитанцию с финальным `status` и ссылкой на результат.

Без этого свойства повторная доставка запроса плодит второй ран — ровно тот класс
дефектов, который контракт обязан исключать.

## 3. Status и result — разные контракты

```
GET {worker}/v1/runs/{runId}/status   → { runId, status, updatedAt }
GET {worker}/v1/runs/{runId}/result   → LaunchResult | 409 (ещё не готово)
```

`status`: `accepted | running | succeeded | failed | cancelled | unknown`.

**Что уже учтено по боевой приёмке (04.10.2026, шлюз 136.65.7.197:8080):**

- `LaunchResult.pid` — **необязателен**: агент в GitHub Actions запущен на другой машине,
  локального PID у нашего API нет. Событие `started` без pid не выдумывается.
- `LaunchResult.repo.commit` — может быть `null` или null-SHA: это «в ветку ничего не
  запушено», а не отказ. Ссылка на файл тогда адресует ветку (`/tree/<branch>/<path>`),
  а не битый `/blob/null/...`; merge ведёт на страницу ветки.
- `logUrl` со схемой `local://` (воркер без бакета) — честный ответ, но не URL:
  `GET /v1/runs/{id}/log` отдаёт ссылку в теле с `retrievable: false`, а не редиректит.
- `status` в `LaunchResult` — `started | failed` про **запуск движка**, а не про исход рана;
  исход несут `exitReason`/`failure`.

`unknown` — исход, который нельзя установить (обрыв связи, смерть воркера без
финализации). Это **не** `failed`: задача не теряется, авто-rerun не происходит,
следующий шаг — reconcile существующего запуска.

## 4. Timeout после dispatch = unknown, затем reconcile

Таймаут ожидания ответа воркера **не** означает, что ран не запущен. Порядок:

1. пометить попытку `unknown` с причиной `worker_unreachable`;
2. **сначала** запросить `status` существующего запуска — ран мог стартовать и даже
   завершиться, пока не было связи;
3. только если запуск не найден — считать его не состоявшимся.

Отмена осиротевшего рана (`cancelOrphan`) остаётся лучшим усилием, но не
заменяет reconcile.

## 5. Два назначения repository — не смешивать

| Назначение | Ветка | Что делается |
|---|---|---|
| Кодовая задача рана | `agent-run/<runId>` | коммит от `baseRevision`, пуш **до** обновления основной ветки; durable-кандидат, переживающий смерть VM |
| Постоянный profile workspace | публикация run branch + versioned canonical merge | следующий Run читает накопленное состояние; конфликт — явный, не «последний победил» |

Основная ветка профиля не меняется автоматически. Смешивать два назначения в одном
repository нельзя: у них разные политики обновления и разный смысл конфликта.

## 6. Тяжёлые выходы — object storage, не git

Git хранит текст/дерево/манифест. Крупные и бинарные выходы — object storage с
хэшами. Ссылка на артефакт обязана быть **доступна конкретному пользователю**:
публичный blob URL из private repo не гарантирует скачивание нашим API-клиентом.
Нужен authenticated retrieval/proxy или scoped URL с принятой доступностью.

## 7. Изоляция воркера объявляется отдельно

Isolation API host может быть `none`, но isolation worker обязана быть отдельно
declared и verified. Snapshot/materialize, артефакты, MCP и interaction-гарантии
**переносятся или заменяются эквивалентом**, а не считаются ненужными из-за удаления
маршрутов.

## 8. Живые события и архив лога — разные контракты

Финальный `logUrl` в GCS не доказывает streaming/cursor replay. GCS-логи приватны,
доступ — scoped. Cleanup VM выполняется после подтверждённой recovery-копии, а не
после одного выхода engine.

## Что это даёт ближайшему deliverable

Один synthetic профиль через наш Task API выполняет настоящий external worker Run:
после рестарта API нет второго запуска, пользователь читает ответ и артефакт,
ephemeral ресурс исчезает только после persist, следующая среда видит сохранённые
данные. До этого #75/#76 не считаются завершённой serverless-миграцией.
